# LiZoneDedup — code artifact

LiZoneDedup is the first complete in-storage deduplication architecture
for ZNS SSDs. This repository holds the **code**: the simulator, the
experiment drivers, the FEMU prototype, and the figure scripts. It
deliberately ships no measurement results — every CSV is regenerated by
running the drivers below.

| Directory | Contents |
|---|---|
| `lzsim/` | **LZSim**, the event-driven, controller-level simulator (source of all throughput/latency numbers) |
| `experiments/` | Experiment drivers (current entry points) and `legacy/` historical batch drivers |
| `femu/` | The FEMU/QEMU prototype: device-side implementation (`lizone.c/.h`), guest benchmark (`liobench.c`), and the one-config launcher (`run_one.sh`) |
| `plotting/` | Figure scripts (`figs_v12.py`) and the numeric anchor checks |
| `spdkhost/` | SPDK host-side prototype: lzd library, lzdtest suite, FEMU device patch

## Quick start (one command, fresh clone)

```bash
python experiments/run_q2.py   # Q2: SimHash vs fp-prefix routing (builds traces on first use, ~15 min)
python experiments/run_q3.py   # Q3: zero-idle sustained pressure + 5% background-reservation runs
```

Requires Python >= 3.10, standard library only.  Workload traces are
materialized automatically into `traces/` on first use.  The FSL trace
additionally needs the public FSL-Homes fingerprint file:
`LZ_FSL_FP=<path> python experiments/run_q2.py` (without it, the fsl rows
of the comparison are skipped and read from the committed
`results_q2/q2_routing.csv`).

## LZSim

LZSim is an original, MQSim-style controller-level model: multi-core
controller pipeline, plane-level NAND units (8 ch × 8 die × 2 plane),
closed-loop QD32 saturation, calibrated to FEMU-default timings
(40/200/2000 µs read/program/erase) so results are comparable with
Hi-ZNS and Balloon-ZNS.

Cost model (µs per 4 KB page; `lzsim/device.py`):

| Operation | Hardware | Software |
|---|---|---|
| SHA-256 | 2.0 (dedicated engine) | 8.0 |
| SimHash digest | — (software-only, 4.0 in both) | 4.0 |
| LZ4 compress | 1.5 (dedicated engine) | 8.0 |
| LZ4 decompress | 1.0 (dedicated engine) | 2.0 |

A "hardware" configuration offloads SHA-256 and LZ4 to dedicated
engines; SimHash exists only in software — the hardware/software arms of
every experiment differ exactly in the SHA/LZ4 offload.

## Reproducing the experiments

```bash
cd experiments
python run_v10.py          # e4 main matrix: 9 systems x 5 workloads
python run_v10b.py         # e4b adaptive-bypass ablation (rocksdb)
python run_v11.py          # v11 review batch: e0/e1b/e5b/e7/e7b/e8/e8b
python run_rerun_all.py    # unified-cost full rerun (e4/e5/e7b/e8b/cloud)
python run_parts.py        # latency decomposition
python run_arms_clean.py   # one batch for the reduction table and Fig. 7
python run_e7_all6.py      # controller-DRAM capacity sweep (Fig. 10a)
python run_v12.py          # migration on/off: long-run allocatable space
python validate.py         # invariant gates every batch must pass

# reviewer-response experiments
python run_q2.py            # SimHash vs fp-prefix routing (full traces)
python run_q3.py            # zero-idle sustained pressure + 5% bg reserve
python run_q4.py            # high-utilization steady state vs global index
```

The workloads are built first (a few minutes; the binary traces are not
checked in):

```bash
python -m lzsim.traces            # all synthetic workloads
python -m lzsim.traces fsl PATH   # fsl from the public FSL-Homes file
```

Each run writes CSVs to `../results_v*/`. Those outputs are not checked
in; produce them locally and point `plotting/figs_v12.py` at the
directory it expects.

## FEMU prototype

`femu/lizone.c` implements the device side (the `dup_append` opcode,
routing, filters, sealing, reset protocol) inside the FEMU zns model;
`femu/liobench.c` is the guest benchmark. Apply `lizone.c/.h` over a
FEMU tree (see FEMU's build docs), boot the prepped guest, and launch a
configuration with `run_one.sh CFG MODE R GEO WORKLOAD`. Set
`FEMU_ROOT` to the built FEMU tree, or run the script from that tree.

**Setup for the paper's Fig. 10 runs.** KVM acceleration
(`-accel kvm -cpu host`), a statically linked `liobench` (the guest is
Debian 12 / glibc 2.36, newer hosts do not run a dynamic binary), an
autorun script that writes to `/dev/console` with `serial-getty@ttyS0`
masked (otherwise the getty steals the tty and every user-space result is
lost), and one FEMU source tweak: `hw/femu/zns/zns.h` sets
`SRAM_WRITE_LATENCY_NS (200000)` so write completion is charged per page
program (write-through), matching the simulator's 40 µs read / 200 µs
program / 2 ms erase table.

**Why Fig. 10 reports the dedup rate, not bandwidth.** The prototype
serialises all dedup bookkeeping under a single global mutex, so every
dedup mode saturates at the same ~300–370 MB/s ceiling regardless of
workload (Oracle, whose hit path is one global map lookup, caps at exactly
the same rate as the full LiZoneDedup path), while NoDedup's own
throughput is set by the write-cache timing model rather than by NAND.
Bandwidth from this prototype therefore measures the critical section,
not the design; LZSim supplies every bandwidth number. The dedup rate is
well defined and comparable.

**Workload fidelity.** The guest workloads must reproduce the simulator's
traces. `liobench.c` mirrors `lzsim/traces.py` for this: the FSL workload
replays the real FSL-Homes user006 fingerprint file (1.69 M 8 KB chunk
hashes, each expanded to two correlated 4 KB pages, exactly as `gen_fsl`
does) and the rocksdb workload re-emits already-live pages to model
same-value overwrites and compaction (as `gen_rocksdb` does, duplicate
fraction p/(1+p)=15.9%). On FSL the prototype's Oracle measures 18.75%,
equal to the trace's exact duplicate rate, which is what confirms the
replay.
